# ADR 0001: 采用服务导向架构

## 状态

已采纳 (2026-05-21)

## 背景

初始系统分析与设计基于面向对象方法（见 `docs/camis-UML.md`），将业务逻辑内聚到实体类上（如 `Activity.generateActivityPlan()`）。经讨论发现该做法与该系统的审批工作流本质存在矛盾。

## 决策

采用**服务导向架构**：

- 实体类是纯数据载体（只保留属性，不包含业务方法）
- 业务逻辑归属服务层（如 `ProjectService.create_project()`, `WorkflowService.transition()`）
- 工作流状态变更由服务层显式驱动，实体不自治

## 理由

1. **系统本质是状态机工作流**，不是一组自治对象。Activity 的状态由不同角色的外部操作驱动变迁，不适合由实体自己执行
2. **跨部门协作**：单个操作的执行者、校验者、被通知者分属不同角色，这些横切逻辑需要协调者（服务层），不属于单一实体
3. **顺序图已指出的矛盾**：UC1-7 的顺序图中所有动作执行者是 `System`，而非实体对象。服务层就是 System 的具体化

## 影响

- 需更新类图：实体类保留属性、去掉方法，新增服务类
- 顺序图的 lifeline `System` 拆分为具体服务
- 已有 FastAPI 代码已采用路由→服务→数据库的分层模式，不需重写
