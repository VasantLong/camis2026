# ADR 0005: 任务驱动导航

## 状态

已实现（v0.19 — P1/P2/P3 完成）

## 背景

CAMIS v0.18.0 界面按功能模块组织（活动管理、仪表盘、个人中心、管理后台）。7 种角色共用同一套页面树，用户登录后需先导航到列表页再筛选才能找到自己的工作入口，认知负荷偏高。

经过用户分析讨论，明确了各角色的行为特征：生产环境无多角色用户，Promoter 同时管 2-3 个活动，GovLiaison 每天集中登记，AdminStaff 的 Dashboard 用于向上汇报而非问题处理等。

## 决策

采用**任务驱动导航**（方案 D），三阶段增量落地：

1. **P1 计数感知**：侧边栏菜单项加实时计数 Badge，用户打开系统即感知"有 N 件事待处理"。后端新增 `GET /activities/counts` 端点
2. **P2 角色首页**：`/` 路由渲染角色感知 HomePage，展示任务卡片+最近活动，替代当前的无脑跳转 `/activities`
3. **P3 任务驱动菜单**：侧边栏从功能分组重构为角色任务菜单（如 GovLiaison 看到"待审查材料④""今日已登记①""全部审批记录"）

## 与 SOA 的关系

任务驱动导航作用于前端 UI 层（用户看到什么、怎么组织菜单），面向服务架构作用于后端逻辑层（服务职责边界、事务管理）。两者正交——前端任务可能编排多个后端服务调用，这是 SOA 的正常消费模式。

P1 的 `GET /activities/counts` 归属 ActivityService。如果未来计数需要跨表聚合，优先前端编排多个轻量端点，不引入聚合层。

## 后果

- 正向：降低用户认知负荷，各角色"打开系统就知道该做什么"
- 正向：增量路线可独立上线验证，不互相阻塞
- 负向：侧边栏从静态配置变为角色驱动生成，维护时需同时考虑菜单项和权限显隐两个维度
- 风险：计数不准确会损害用户信任，计数逻辑需充分测试
